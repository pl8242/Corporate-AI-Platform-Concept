## 1. Назначение и принципы

### 1.1. Назначение

Персональный аудит — автоматически формируемый ИИ-СТО аналитический отчёт о подтверждённой деятельности сотрудника за установленный период.

Аудит должен отвечать на вопросы:

1. Над чем работал сотрудник?
2. Что завершено за отчётную неделю?
3. Что осталось незавершённым?
4. Как изменилась ситуация относительно предыдущей недели?
5. Какие тенденции наблюдаются за несколько недель?
6. Какие задержки, блокировки и риски подтверждены?
7. Какие действия могут улучшить рабочий процесс?

Аудит описывает результаты и движение работы, а не личные качества сотрудника.

Обязательная формулировка в каждом HTML:

**Данные аудита не являются итоговой оценкой продуктивности сотрудника.**

### 1.2. Универсальность

Шаблон применяется ко всем подразделениям, включённым в контур ИИ-СТО.

В шаблоне не фиксируются:

- конкретные подразделения;
- сотрудники;
- должности;
- проекты Jira;
- репозитории Git;
- учётные записи;
- даты пилотных запусков.

Все перечисленные параметры определяются при выполнении аудита.

Шаблон не предполагает обязательной разработки программного кода каждым сотрудником.

Отсутствие PR/MR, коммитов или ревью не является доказательством отсутствия работы.

### 1.3. Связь с генеральным отчётом

Персональный аудит — самостоятельный аналитический продукт отдельного процесса. Генеральный отчёт определяет общие правила расчёта и управленческой интерпретации; персональный аудит использует те же факты и определения, раскрывая деятельность сотрудника глубже, по применимым источникам.

Аудит должен соответствовать требованиям management-report, включая:

- единые периоды;
- идентификацию сотрудников;
- определения общих метрик;
- пороги существенности;
- требования к достоверности;
- правила публикации;
- контракт персональных файлов по п. 3.5 генерального шаблона.

Персональные аудиты формируются до генерации генерального отчёта.

Отсутствие аудита не блокирует генеральный отчёт и фиксируется в его п. 3.6; отчётный агент не генерирует персональные аудиты самостоятельно.

Агент не вправе самостоятельно менять согласованную методику.

### 1.4. Основные принципы

- Только проверяемые данные.
- Единая методика расчётов.
- Исторические состояния восстанавливаются по истории.
- Факты отделяются от гипотез.
- Неприменимые показатели не используются для оценки работы.
- Недоступные данные не заменяются нулями.
- Анализируется собственная динамика сотрудника.
- Рейтинги и сравнения сотрудников запрещены.
- HTML должен быть понятен без доступа к исходным системам.

### 1.5. Первый шаг запуска

Первый шаг каждого запуска: прочитать из репозитория этот шаблон и шаблон management-report.

Работа по памяти или прошлым сообщениям запрещена.

Если любой из двух шаблонов недоступен — остановиться с явным сообщением об ошибке.

### 2.1. Состояния показателей

Используются четыре состояния, предусмотренные генеральным шаблоном.

| Состояние | Значение |
|---|---|
| 0 | События отсутствуют, полнота соответствующей выборки подтверждена |
| не собирается | Сбор показателя не предусмотрен или не реализован |
| временно недоступно | Источник или сервис временно недоступен |
| не удалось определить | Данных недостаточно для достоверного расчёта |

**«Не применяется» — отдельный признак применимости, а не пятое состояние сбора данных.**

Применимость устанавливается по подтверждённому характеру деятельности и доступной информации, а не только по наличию событий.

Если невозможно установить, должен ли показатель применяться, агент фиксирует неопределённость и не объявляет его неприменимым автоматически.

## 3. Источники и идентификация

### 3.1. Источники

Используются существующие сервисы IT.

| Источник | Назначение |
|---|---|
| Канонический справочник | Сотрудники, подразделения, идентификаторы и соответствия |
| Jira | Задачи, исполнители, статусы, сроки, история |
| GitHub/GitLab | Изменения, PR/MR, коммиты, ревью |
| Архив собранных данных | История, сравнительный фон, восстановление состояний |
| Общие расчёты ИИ-СТО | Контроль согласованности с генеральным отчётом |

Источники применяются по доступности и релевантности.

Создание новых интеграций не входит в задачу аудита.

### 3.2. Идентификация сотрудника

Перед сбором агент получает:

- employee-id;
- ФИО;
- подразделение;
- идентификатор Jira;
- подтверждённые GitHub/GitLab-аккаунты;
- другие существующие соответствия, необходимые для доступных источников.

Единственным основанием сопоставления служит канонический справочник.

При нескольких подтверждённых аккаунтах одного сотрудника данные объединяются без двойного подсчёта.

Если сотрудник относится к нескольким подразделениям, применяются подтверждённые правила атрибуции.

### 3.3. Jira: правила получения

Запросы Jira по сотруднику должны использовать канонический идентификатор, а не ФИО или Git-логин.

Порядок:

1. Получить Jira ID из справочника.
2. Определить поддерживаемый тип идентификатора в подключённой Jira.
3. Сформировать JQL через существующий сервис IT.
4. Проверить успешность запроса.
5. Проверить полноту выборки, включая пагинацию.
6. Проверить принадлежность возвращённых задач.
7. Сохранить результат и сведения о проверке.

Для Jira Cloud обычно применяется accountId, но конкретный формат определяется действующим контрактом сервиса.

Если JQL вернул пустую выборку, агент обязан отличить подтверждённое отсутствие задач от ошибки или неполного поиска.

История назначений учитывается при определении принадлежности задач за прошлые периоды.

**Область персональной выборки.** Персональная выборка опирается на ту же подтверждённую область проектов подразделения, что и генеральный отчёт. Персональная JQL используется как способ поиска и проверки, но не создаёт другую область учёта: задача, над которой сотрудник работал, но перестал быть её исполнителем, находится по истории назначений и входит в его показатели за соответствующие недели по правилам п. 4.5.

**Единая атрибуция задач** (совпадает с п. 3.4 генерального шаблона):

- завершённая задача приписывается сотруднику по подтверждённому исполнителю на момент завершающего перехода задачи в Done;
- незавершённая задача — по исполнителю на конец отчётной недели;
- участие других сотрудников по истории назначений может отражаться в жизненном цикле задачи, но не увеличивает счётчик завершённых задач.

### 3.4. GitHub/GitLab: правила получения

Агент использует только подтверждённые Git-аккаунты.

При сборе различаются:

- авторство изменений;
- создание PR/MR;
- слияние PR/MR;
- изменение существующих PR/MR;
- участие в ревью;
- открытые PR/MR на дату среза.

Собственные review-комментарии не учитываются как ревью чужой работы.

Имена проверяющих в пользовательском отчёте не выводятся.

**Связи Jira ↔ Git подтверждаются только по Jira-ключу в PR/MR или коммитах. Неподтверждённые PR/MR не распределяются по задачам.**

Технические различия GitHub и GitLab обрабатываются существующими сервисами IT.

### 3.5. Контроль источников

Перед расчётом агент проверяет:

- Сотрудник найден в справочнике.
- Подразделение определено.
- Идентификаторы сопоставлены.
- Использованы существующие сервисы IT.
- Запросы выполнены успешно или ошибки зафиксированы.
- Пагинация и границы выборки проверены.
- Данные сохранены для последующих расчётов.
- Несопоставленные объекты не приписаны сотруднику предположительно.

## 4. Периоды и методика расчётов

### 4.1. Отчётный период

Одна завершённая ISO-неделя.

Границы:

[понедельник 00:00; следующий понедельник 00:00)

Часовой пояс: Europe/Moscow.

Идентификатор: YYYY-Www.

Правая граница интервала не включается.

### 4.2. Основное сравнение двух недель

Обязательно сравниваются:

- отчётная неделя;
- непосредственно предшествующая базовая неделя.

Для каждого применимого и сопоставимого показателя рассчитываются:

- значение базовой недели;
- значение отчётной недели;
- абсолютное изменение;
- относительное изменение, если расчёт корректен.

При нулевой базе относительное изменение не вычисляется искусственно.

### 4.3. Четырёхнедельный фон

Обязательно используются четыре полные недели, предшествующие отчётной.

Базовая неделя входит в этот фон.

Таким образом, анализ охватывает до пяти последовательных недель.

Четырёхнедельный фон необходим для:

- выявления устойчивых изменений;
- проверки разовых отклонений;
- оценки динамики завершения работы;
- выявления накопления незавершённых объектов.

Если доступны все четыре сопоставимые недели, допускается расчёт медианы.

Если история неполна, агент показывает доступные данные и указывает:

**«Недостаточно данных для устойчивого тренда».**

Отсутствующие значения не заполняются нулями.

Утверждение о тренде допускается только при соблюдении требований п. 3.3 генерального шаблона.

### 4.4. Исторические состояния

Показатели прошлых периодов рассчитываются на соответствующие исторические даты.

Текущий статус не используется вместо исторического без проверки событий.

Для незавершённой работы фиксируются:

- состояние на конец периода;
- дата среза;
- возраст объекта на дату среза.

**Дата среза всегда равна правой границе отчётного периода (следующий понедельник 00:00). Срез в момент подготовки запрещён. Состояния на конец периода восстанавливаются по истории изменений (Jira, Git) — так же, как для базы сравнения. Если восстановление невозможно, показатель получает статус «не удалось определить», а не срезается на другой момент.**

Если восстановить историческое состояние нельзя, показатель отмечается как неопределённый.

### 4.5. Методика Jira

Для задач могут рассчитываться:

- завершено за период;
- в работе на конец периода;
- просрочено на дату среза;
- изменило статус за период;
- подтверждённо заблокировано;
- осталось незавершённым.

Определения статусов, правила включения задач и **единая атрибуция завершения (п. 3.3)** должны соответствовать генеральному шаблону.

Задачи учитываются по подтверждённой принадлежности сотруднику.

Одна задача не должна дублироваться внутри одного показателя.

Завершение задачи не приравнивается автоматически к production-релизу.

### 4.6. Методика Git

| Показатель | Правило |
|---|---|
| Создано PR/MR | Дата создания попадает в период |
| Слито PR/MR | Дата слияния попадает в период |
| Обновлено PR/MR | Подтверждённое значимое изменение в периоде по принятой методике |
| Открыто PR/MR | PR/MR остаётся открытым на дату среза |
| Возраст PR/MR | Время от создания до даты среза |
| Проверено чужих PR/MR | Количество уникальных чужих PR/MR с подтверждённым ревью сотрудника в периоде |
| Approvals | Подтверждённые события одобрения, отдельно от количества уникальных PR/MR |
| Внешняя реакция | Подтверждённое действие другого участника |
| Связь с Jira | Подтверждённая связь PR/MR с задачей по п. 3.4 |

Созданные, слитые и обновлённые PR/MR — разные показатели.

PR/MR, созданный ранее и слитый в отчётную неделю, учитывается в слияниях, но не в новых PR/MR этой недели.

Повторные ревью одного PR/MR не увеличивают число уникальных проверенных PR/MR.

### 4.7. Контроль расчётов

- Границы периодов корректны.
- Базовая неделя определена.
- Четырёхнедельный фон рассчитан или ограничение указано.
- Исторические состояния не заменены текущими.
- Значения проверены на дублирование.
- Создание, обновление и завершение не смешаны.
- Нулевые и неизвестные значения различаются.
- Процентные изменения рассчитаны корректно.
- Применимость каждого показателя определена.
- Дата среза соответствует п. 4.4.

## 5. Применимость показателей

### 5.1. Общий принцип

Агент определяет применимость показателей до построения аналитических выводов.

Применимость устанавливается по подтверждённому характеру деятельности сотрудника (канонический справочник, подтверждённые обязанности), а не по наличию событий и не по наличию технического доступа к системе. Доступ — условие возможности сбора данных, не признак применимости.

Для сотрудника с подтверждённой разработкой Git-показатели выводятся всегда, включая нулевые значения (подтверждённый ноль). При отсутствии подтверждённого вида деятельности показатели получают признак «не применяется»; при неустановленной применимости — статус «не удалось определить».

### 5.2. Категории показателей

**Задачи и результаты**

- завершённые задачи;
- задачи в работе;
- просроченные задачи;
- изменения статусов;
- подтверждённые блокировки.

**Разработка и интеграция**

- созданные PR/MR;
- слитые PR/MR;
- открытые PR/MR;
- ревью чужих PR/MR;
- возраст открытых изменений.

**Общие показатели процесса**

- динамика завершения работы;
- накопление незавершённых объектов;
- подтверждённые задержки;
- качество трассируемости;
- ограничения данных.

### 5.3. Правила представления

Если Git не относится к деятельности сотрудника, Git-показатели не включаются в его ключевые KPI.

Если Git относится к деятельности сотрудника, но за неделю подтверждённо не было событий, допустимо значение 0.

Если Git-источник недоступен, отсутствие событий не утверждается.

Если сотрудник работает и с Jira, и с Git, оба набора показателей могут использоваться одновременно.

Единая структура аудита сохраняется, но не все разделы обязаны содержать числовые показатели.

## 7. Примеры заполнения

Все примеры в этом разделе демонстрационные. Значения, идентификаторы и ситуации вымышлены. Агент не должен переносить их в реальные аудиты.

### 7.1. Пример: сотрудник с активностью в Jira, без применимых Git-показателей

**Краткий вывод**

За отчётную неделю сотрудник завершил 5 задач, продолжил работу над 3 задачами. Одна задача имеет подтверждённое превышение установленного срока на 2 дня. Относительно предыдущей недели количество завершённых задач увеличилось с 3 до 5.

Git-показатели к данному аудиту не применяются.

**Главное наблюдение**

Подтверждён рост числа завершённых задач. Одновременно сохраняется одна просроченная задача, причина задержки по доступным данным не установлена.

**Недопустимый вывод**

«Сотрудник работает эффективнее на 67%».

Количество завершённых задач само по себе не доказывает сопоставимую трудоёмкость или качество работы.

### 7.2. Пример: сотрудник с Git-активностью

**Основные показатели**

| Показатель | Значение |
|---|---|
| Создано PR/MR | 3 |
| Слито PR/MR | 2 |
| Проверено чужих PR/MR | 4 |
| Открытых авторских PR/MR | 5 |

**Главное наблюдение**

В отчётном периоде создано три PR/MR и слито два. На дату среза остаются пять открытых авторских PR/MR, включая ранее созданные. Два из них не имеют подтверждённой внешней реакции.

**Ограничение**

Отсутствие зафиксированного ревью в Git не доказывает отсутствие обсуждения в других каналах.

### 7.3. Пример: сравнение двух недель

| Показатель | Базовая | Отчётная | Изменение |
|---|---|---|---|
| Завершено задач | 3 | 5 | +2 |
| Просрочено на конец недели | 2 | 1 | −1 |
| В работе на конец недели | 4 | 3 | −1 |

**Корректная интерпретация**

Число завершённых задач выросло на две, а количество просроченных задач на конец недели сократилось с двух до одной. Для оценки устойчивости изменения необходимо учитывать четырёхнедельный фон и сопоставимость задач.

### 7.4. Пример: четырёхнедельный фон

| Неделя | Завершено задач |
|---|---|
| W-4 | 4 |
| W-3 | 5 |
| W-2 | 3 |
| W-1 | 3 |
| W | 5 |

Медиана четырёх предыдущих недель: 3,5.

**Корректная интерпретация**

Показатель отчётной недели выше медианы предыдущих четырёх недель. Однако аналогичное значение уже встречалось, поэтому одного этого наблюдения недостаточно для утверждения устойчивого роста. Существенность отклонения оценивается по правилам п. 8.2.

### 7.5. Пример: риск и рекомендация

**Риск**

Три открытых PR/MR не имеют подтверждённой внешней реакции на дату среза.

**Возможное влияние**

Если изменения ожидают ревью, это может задерживать их интеграцию.

**Уверенность**

Высокая — в факте отсутствия зарегистрированной реакции. Средняя — в предположении о причине задержки.

**Рекомендация**

Предлагается проверить необходимость ревью по этим PR/MR и определить следующий шаг для каждого.

Предлагаемый владелец: технический руководитель команды.

Предлагаемый срок: в течение следующей рабочей недели.

Статус: предложение ИИ-СТО, не согласованное поручение.

### 7.6. Пример: недостаточные данные

Показатель: завершено задач.

Состояние: временно недоступно.

Причина: сервис Jira не ответил при получении истории задач.

**Корректный вывод**

«Не удалось достоверно определить количество завершённых задач за период».

**Недопустимый вывод**

«Сотрудник не завершил ни одной задачи».

## 8. Правила аналитических выводов

### 8.1. Факты и гипотезы

Каждый вывод должен опираться на проверенные данные.

Факты и возможные объяснения не смешиваются.

Если причина задержки не установлена, агент прямо указывает это.

### 8.2. Существенность

Пороги существенности и правила определения трендов берутся из п. 3.3 генерального шаблона. На персональном масштабе применяются следующие правила:

- качественные изменения (появление или исчезновение явления) — выделяются как персональные наблюдения при переходе 0 → ненуль и наоборот;
- количественные изменения — выделяются как персональные наблюдения при изменении не менее чем на 3 единицы либо при переходе через нулевую базу (0 → N, N → 0);
- изменения ниже порогов — только наблюдение в разделе 6.4, без рисков и рекомендаций.

Вводить собственные пороги без согласования запрещено.

Персональные пороги определяют, что попадает в наблюдения аудита, и не являются управленческой существенностью. Управленческая существенность (пункты раздела 3.1 генерального отчёта) определяется только по порогам п. 3.3 генерального шаблона; персональные наблюдения не переносятся в генеральный отчёт как управленческие пункты. Рекомендации аудита остаются предложениями, а не поручениями.

Пороги относятся только к количественной динамике показателей. Самостоятельно подтверждённые фактические риски (блокировки, просрочки, распознаваемые по правилам п. 3.1 генерального шаблона) фиксируются в аудите как факты независимо от порогов и количественных изменений.

### 8.3. Запрет персональных оценок

Не допускаются:

- рейтинги сотрудников;
- сравнение сотрудников между собой;
- выводы о профессионализме по количеству событий;
- обвинительные формулировки;
- предположения о мотивации и дисциплине.

### 8.4. Проверка аналитики

- Каждый вывод подтверждён фактами.
- Гипотезы явно обозначены.
- Причины не придуманы.
- Нет сравнения сотрудников.
- Нет выводов о личных качествах.
- Отсутствие Git-активности не трактуется как отсутствие работы.
- Рекомендации не выданы за поручения.

## 9. Качество данных и сверка

### 9.1. Единая методика

Сопоставимые показатели персонального и генерального отчётов должны использовать одинаковые определения.

### 9.2. Сверка

Агент проверяет:

- Состав сотрудников.
- Корректность соответствий учётных записей.
- Отсутствие двойного подсчёта.
- Соответствие KPI детальным таблицам.
- Совпадение периодов.
- Согласованность с общими расчётами генерального отчёта.

**Общие расчёты ИИ-СТО** — промежуточные агрегаты подразделения, рассчитанные аудит-процессом по исходным данным недели по правилам генерального шаблона до публикации генерального отчёта. Сверка выполняется с этими расчётами.

После публикации генерального отчёта фактические расхождения с его цифрами фиксируются в «Качестве данных» аудита следующей итерации и передаются владельцу шаблона.

Не допускается циклическая зависимость, при которой персональные аудиты ожидают готового генерального отчёта, а генеральный отчёт ожидает персональные аудиты.

### 9.3. Аддитивность

Суммировать персональные показатели разрешено только там, где метрика аддитивна и исключён двойной подсчёт.

Например, один PR/MR может получить ревью нескольких сотрудников. Сумма индивидуальных показателей ревью не обязана совпадать с количеством уникальных PR/MR, проверенных командой.

### 9.4. Расхождения

При обнаружении расхождения фиксируются:

- показатель;
- значения;
- величина расхождения;
- возможная причина;
- статус проверки.

Агент не исправляет расхождения предположительно.

### 9.5. Контроль качества

- Идентификация подтверждена.
- Выборки проверены на полноту.
- KPI соответствуют детализации.
- Исторические состояния корректны.
- Нет двойного подсчёта.
- Неприменимые и недоступные показатели различаются.
- Расхождения зафиксированы.
- Ограничения явно отражены.

## 10. Технические требования

### 10.1. Формат результата

Для каждого сотрудника формируется отдельный HTML-файл.

HTML должен:

- корректно отображать кириллицу;
- содержать все обязательные разделы;
- иметь читаемые таблицы;
- показывать значения и статусы доступности;
- поддерживать ссылки на подтверждённые первоисточники;
- быть понятным без обращения к Jira и Git.

### 10.2. Путь к файлу

Нормативный путь:

**[ПУТЬ_К_ПЕРСОНАЛЬНЫМ_ОТЧЁТАМ]/YYYY-Www/<employee-id>.html**

Пример: employees/2026-W46/i.kochubey.html

Базовый каталог [ПУТЬ_К_ПЕРСОНАЛЬНЫМ_ОТЧЁТАМ] задаётся конфигурацией и совпадает с каталогом, в котором генеральный отчёт ищет персональные файлы (п. 3.5 генерального шаблона).

employee-id берётся только из канонического справочника.

ФИО не используется как технический идентификатор файла.

### 10.3. Запрет перезаписи

Автоматическая перезапись существующего файла запрещена.

Если файл существует, агент фиксирует конфликт и не заменяет его. Процедура исправления — п. 10.10.

### 10.4. Ссылки

Разрешены подтверждённые ссылки на:

- задачи Jira;
- PR GitHub;
- MR GitLab.

В HTML отображаются понятные идентификаторы и названия объектов.

URL берутся из фактических данных.

Ссылки на API и технические сервисы IT в пользовательском HTML запрещены.

Если URL не подтверждён, отображается текст без вымышленной ссылки.

Запрет ссылок на интерфейс GitHub/GitLab в чек-листе генерального отчёта распространяется на материалы отчёта и не запрещает ссылки на PR/MR в персональном аудите.

### 10.5. Самодостаточность

Все основные показатели, статусы, наблюдения, риски и рекомендации должны быть видны в самом HTML.

Дополнительные ссылки не заменяют содержание отчёта.

### 10.6. Последовательность формирования

1. Прочитать оба шаблона из репозитория (п. 1.5).
2. Определить подразделения и сотрудников.
3. Получить и проверить идентификаторы.
4. Получить данные через существующие сервисы IT.
5. Сохранить исходные данные.
6. Рассчитать показатели.
7. Выполнить сверку с общими расчётами.
8. Сформировать персональные HTML.
9. Проверить качество файлов.
10. Сохранить файлы по нормативным путям.
11. Сформировать реестр файлов и сводный индекс (п. 14); передать их процессу формирования генерального отчёта.

Персональные HTML должны существовать до генерации генерального HTML.

### 10.7. Повторное использование данных

Исходные данные и расчёты сохраняются отдельно от HTML.

Повторная генерация представления из сохранённых данных не должна инициировать новый полный сбор.

Если требуется актуализировать состояние объектов, такое обновление выполняется отдельно и фиксируется.

### 10.8. Публикация

В пилотном режиме результаты не публикуются автоматически в рабочие чаты до согласования.

Порядок последующей публикации определяется общим процессом ИИ-СТО.

### 10.9. Доступ

Файлы публикуются в защищённом хранилище: корпоративный HTTPS, серверная авторизация, разграничение прав.

Доступ к аудиту определяется правами на хранилище, а не на чат.

### 10.10. Исправление файла

Перезапись уже сохранённого файла запрещена (п. 10.3).

Если сохранённый аудит требует исправления до публикации генерального отчёта:

- создаётся новая версия файла `<employee-id>-v2.html` (далее v3 и так далее);
- предыдущая версия сохраняется;
- причина исправления фиксируется в реестре файлов;
- генеральный отчёт ссылается на актуальную версию из реестра.

Актуальной считается версия, указанная в реестре файлов аудитов. Ссылки на персональный аудит (в генеральном отчёте и сводном индексе) формируются исключительно по записям реестра со статусом «сформирован»; при отсутствии реестра либо записи сотрудника ссылка не создаётся. Базовый файл `<employee-id>.html` остаётся неизменным и используется только тогда, когда он указан в реестре как актуальная версия.

Исправление после публикации генерального отчёта выполняется по решению владельца шаблона и отражается в «Качестве данных» следующей итерации.

### 10.11. Технический чек-лист

- HTML создан.
- Кириллица отображается корректно.
- Обязательные разделы присутствуют.
- Таблицы и значения согласованы.
- Ссылки проверены.
- Технических API-ссылок нет.
- Файл сохранён по полному нормативному пути (п. 10.2).
- Существующие файлы не перезаписаны.
- Реестр файлов сформирован.
- Генеральный отчёт может обнаружить сохранённые аудиты.

## 11. Обработка ошибок

### 11.1. Недоступность источника

При недоступности источника агент фиксирует:

- источник;
- время;
- тип ошибки;
- затронутые показатели;
- влияние на полноту аудита.

Недоступные значения не заменяются нулями.

### 11.2. Ошибки идентификации

Несопоставленные учётные записи не приписываются сотрудникам предположительно.

### 11.3. Противоречия в расчётах

Если KPI не соответствует детализации, агент проверяет расчёт.

Противоречивые показатели не должны выдаваться за подтверждённые.

### 11.4. Недостаток истории

Недостающие недели не заполняются нулями.

Обязательный раздел сравнительного фона сохраняется с указанием ограничения.

### 11.5. Неприменимые показатели

Неприменимость должна иметь подтверждённое основание.

Отсутствие событий само по себе не доказывает неприменимость показателя.

### 11.6. Невозможность формирования аудита

Если данных недостаточно для достоверного персонального аудита, агент:

- фиксирует причину;
- указывает затронутые источники;
- не создаёт вымышленные показатели;
- отражает статус в реестре результатов;
- не объявляет аудит успешно принятым.

## 12. Чек-лист приёмки

Аудит считается успешно сформированным только после выполнения обязательных проверок.

**Идентификация и источники**

- Сотрудник найден в каноническом справочнике.
- Подразделение определено.
- Jira ID проверен.
- Git-аккаунты сопоставлены, если применимо.
- Источники получены или ограничения зафиксированы.
- Оба шаблона прочитаны из репозитория первым шагом (п. 1.5).

**Расчёты**

- Отчётная неделя определена корректно.
- Базовая неделя определена.
- Четырёхнедельный фон присутствует или ограничение указано.
- Исторические состояния проверены.
- Дата среза соответствует правой границе отчётного периода (п. 4.4); срез в момент подготовки не использован.
- Применимость показателей определена.
- KPI согласованы с детализацией.
- Двойной подсчёт исключён.
- Атрибуция задач соответствует единому правилу п. 3.3.

**Аналитика**

- Краткий вывод подтверждён фактами.
- Незавершённая работа отражена.
- Риски имеют основания.
- Гипотезы отделены от фактов.
- Рекомендации обозначены как предложения.
- Нет рейтингов и сравнений сотрудников.
- Отсутствие Git-активности не трактуется как отсутствие работы.
- Изменения ниже порогов п. 8.2 не превращены в риски; самостоятельно подтверждённые фактические риски (блокировки, просрочки) отражены независимо от порогов.

**Качество и согласованность**

- Ограничения данных указаны.
- Недоступные значения не заменены нулями.
- Расхождения с общими расчётами проверены.
- Источники и время получения указаны.

**HTML и публикация**

- HTML самодостаточен.
- Ссылки ведут на подтверждённые первоисточники.
- API-ссылки отсутствуют.
- Путь соответствует [ПУТЬ_К_ПЕРСОНАЛЬНЫМ_ОТЧЁТАМ]/YYYY-Www/<employee-id>.html и совпадает с каталогом поиска генерального отчёта.
- Существующие файлы не перезаписаны; исправления выполнены по п. 10.10.
- Реестр и сводный индекс сформированы; ссылки на аудит ведут только на записи реестра со статусом «сформирован».
- Аудит подготовлен до генерального отчёта.
- Пилотный аудит не опубликован без согласования.

## 13. Запреты и ограничения

Агенту запрещено:

1. Жёстко закреплять подразделение, сотрудника или проект в шаблоне.
2. Считать Git-активность обязательной для всех сотрудников.
3. Трактовать отсутствие PR/MR как отсутствие работы.
4. Использовать ФИО вместо канонических идентификаторов Jira.
5. Создавать новый справочник вместо существующего.
6. Приписывать несопоставленные события сотруднику предположительно.
7. Заменять недоступные данные нулями.
8. Подменять исторические состояния текущими.
9. Смешивать созданные, обновлённые и слитые PR/MR.
10. Дважды учитывать один объект внутри одного показателя.
11. Придумывать причины задержек.
12. Сравнивать сотрудников между собой.
13. Показывать имена проверяющих.
14. Оценивать личные качества сотрудника по количеству событий.
15. Изменять методику генерального отчёта.
16. Создавать несуществующие ссылки.
17. Выводить ссылки на технические сервисы IT.
18. Выдавать рекомендации за согласованные поручения.
19. Перезаписывать существующие аудиты.
20. Публиковать пилотные результаты без согласования.
21. Использовать персональную JQL-выборку как другую область учёта (см. п. 3.3).
22. Создавать сводный документ с показателями нескольких сотрудников; сводный индекс (п. 14) содержит только ссылки и статусы.

## 14. Результат работы агента

Для каждого подразделения, включённого в запуск, агент должен подготовить:

1. Персональные HTML-аудиты сотрудников области запуска. Для каждого сотрудника области запуска фиксируется статус: сформирован / не сформирован с причиной — даже при отсутствии подтверждённых событий за неделю.
2. Реестр файлов в машиночитаемом виде (JSON рядом с HTML, например `employees/YYYY-Www/audit-registry.json`): employee-id, версия файла, путь, статус (сформирован / не сформирован с причиной), дата среза. Генеральный отчёт читает реестр как первоисточник ссылок; ссылка на аудит создаётся только для записей со статусом «сформирован».
3. Сводный индекс аудитов `employees/YYYY-Www/audit-index.html`: employee-id, ФИО, статус, ссылка на актуальную версию по реестру. Индекс не содержит показателей, сводных цифр и сравнений сотрудников — только ссылки и статусы. Индекс не заменяет персональные файлы и не является источником данных для генерального отчёта.
4. Сохранённые исходные данные и расчёты.
5. Протокол ошибок, ограничений и неполных сопоставлений.
6. Результат сверки с общими расчётами генерального отчёта.

Ключевое требование: персональный аудит должен отражать подтверждённую деятельность сотрудника по применимым источникам, показывать динамику и ограничения процесса, не превращаясь в оценку человека по количеству задач или Git-событий.
