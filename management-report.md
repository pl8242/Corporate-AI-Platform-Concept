# 1. Назначение

Агент формирует развёрнутый управленческий отчёт по работе IT-подразделения ТЕМА за последнюю завершённую календарную неделю на основе Jira, GitHub, GitLab и канонического справочника сотрудников. Краткая версия публикуется в теме генерального чата. Полная версия сохраняется в репозитории как Markdown и предоставляется руководителям в формате HTML через защищённый корпоративный HTTPS-адрес.

Первый шаг каждого запуска: прочитать этот шаблон из репозитория.

Если шаблон недоступен — остановиться с явным сообщением об ошибке.

Работать по памяти или по прошлым сообщениям запрещено.

Промпт-запуск (в чат каждую неделю; при автоматизации зашит в триггер):

---

Не используй контекст прошлых сообщений. Прочитай шаблон отчёта из репозитория [ПУТЬ_К_ФАЙЛУ] и выполни его в полном объёме для подразделения ТЕМА, включая правила отбора данных и определения периодов из шаблона.

---

# 2. Правила отбора данных

- Свежая независимая выборка: прошлые сообщения, прошлые отчёты и результаты личных агентов не используются. Исключение — архивный отчёт подразделения (используется в п. 3.3, 3.4, 3.6): читается только для согласованности названий направлений и оценки устойчивости трендов, не как источник данных.

- Неделя: интервал с понедельника 00:00 включительно до следующего понедельника 00:00 исключительно (полузакрытый: [пн 00:00, пн 00:00)), часовой пояс Europe/Moscow. Данные с отметкой ровно на границе относятся к новой неделе. Отчётный период — последняя завершённая неделя, база сравнения — предшествующая ей завершённая неделя. Текущую неполную неделю не включать.

- События и состояния различаются строго.

Событие — действие внутри границ недели (слит PR, переход задачи в Done, коммит, review чужого PR/MR). Состояние — положение на момент конца недели (открытый хвост PR/MR, открытые авторские PR/MR, задачи без срока, просроченные).

Показатели состояний прошлой недели восстанавливаются только по истории изменений (Jira) и истории Git на момент конца прошлой недели.

Использовать текущее состояние источников для расчёта базы сравнения запрещено: текущая выборка может как исключать закрытые с тех пор PR, так и включать вновь созданные — результат сравнения будет искажён.

- Проверка источников до анализа: агент убеждается, что Jira, GitHub, GitLab доступны и период покрыт данными полностью. Недоступный источник —

помечается в «Качестве данных» как «временно недоступно», зависящие от него разделы собираются частично с явной пометкой.

Агент проверяет доступность только своих источников и доставку только своего отчёта. Инфраструктурные сбои он фиксирует, но не диагностирует и не устраняет — он не дежурный по платформе.

- Область данных: только подтверждённые проекты Jira подразделения ТЕМА и связанные репозитории. Чужие проекты не приписывать.

- Выборка задач — все задачи подтверждённых проектов подразделения, без фильтрации по исполнителям. Канонический справочник используется только для отображения ФИО. Если исполнитель не сопоставлен со справочником — задача не исключается, исполнитель указывается как в Jira; расхождение фиксируется в «Качестве данных».

- Завершённые задачи — уникальные, по истории переходов в Done (повторные переходы не удваивают задачу).

- Связи Jira↔Git подтверждаются только по Jira-ключу в PR/MR или коммитах.

PR/MR без связи не исключаются из Git-анализа, но задачам не приписываются.

- Счётчики (если используются) — контрольные значения, не пересчитывать.

При расхождении счётчика с независимой выборкой сохраняются обе цифры, расхождение объясняется в «Качестве данных».

# 3. Структура отчёта

## 3.0 Статус недели

Первая строка после заголовка отчёта:

«Статус: в графике / под риском / есть отставание / не определён —

[одна строка причины]».

Определение по лестнице, сверху вниз — первый подходящий уровень:

1. Срыв срока задачи или поставки, помеченной план-маркером (контрольная точка, метка релиза, высокий приоритет), либо массовые просрочки обычных задач → «есть отставание» с указанием факта.

Одиночная просрочка задачи обычного приоритета без блокировки —

не статус уровня 1, а материал для п. 3.1.

Переносы сроков, согласованные до наступления исходной даты, отставанием не считаются; передвинутые сроки остаются триггером п. 3.1.

2. Просрочек уровня 1 нет, но есть план-маркеры (контрольные точки, приоритет релиза в названии или метках задач, назначенные сроки поставки) → «в графике» или «под риском» по их состоянию.

3. Ни просрочек уровня 1, ни план-маркеров → «не определён: недостаточно данных о плане» с перечнем, чего не хватает.

Критичность задачи определяется только по данным: план-маркеры, приоритет, метки — не по впечатлению агента.

Примеры формулировок:

«Статус: в графике — ключевые задачи недели в Testing по плану, блокировок нет».

«Статус: под риском — Release Candidate не вышел в production, планируемая дата публикации под вопросом».

«Статус: есть отставание — контрольная точка релиза сорвана, 2 задачи с меткой «release» просрочены более чем на неделю».

«Статус: не определён — в проектах нет контрольных точек и приоритетов релиза, просрочек нет».

Причина — конкретный факт из данных недели, не общая формулировка.

Уровень «не определён» допустим только после проверки пунктов 1–2 —

не использовать его как отговорку по умолчанию.

## 3.1 На что обратить внимание

Раздел идёт сразу после статуса недели: решения не должны дожидаться детализации ниже. Триггеры и правила формирования от места в структуре не зависят.

До 4 существенных пунктов; формируются только из найденных фактов.

Маркеры: 🔴 — блокировки, возвраты из Done, просрочки; 🟡 — умеренные риски.

Агент проверяет неделю по списку триггеров и формирует пункты только из сработавших:

—  значимые задачи в Done без подтверждённого выхода в production (высокий приоритет или пометка релиза, либо в проекте заведена стадия поставки). Остальные Done-задачи без выхода — агрегат в статистике п. 3.3, не пункт;

—  просроченные задачи и задачи с передвинутым сроком;

—  возвраты из Done в работу;

—  рост задач без срока;

—  PR/MR, слитые без независимого review;

—  PR/MR, открытый более 14 календарных дней, при связанной задаче в активных статусах (в работе, review, testing);

—  CHANGES_REQUESTED без снятия замечания более 3 рабочих дней;

—  PR/MR без подтверждённой Jira-связи не признаются автоматически безопасными: существенные задержки и блокировки таких PR/MR анализируются отдельно, без приписывания их конкретным Jira-задачам — доказательства приводятся по Git-фактам без выдуманных ключей;

—  несопоставленные со справочником исполнители;

—  аномалии динамики по п. 3.3: устойчивые тренды и разовые существенные отклонения (по порогам п. 3.3); отклонения ниже порогов — не пункт.

Если сработавших триггеров более четырёх — выбираются наиболее значимые по влиянию на: сроки поставки, пользователей, критические процессы, наличие подтверждённой блокировки (приоритет и метки — источник значимости, не впечатление агента). Остальные факты не скрывать: статистика п. 3.3 показывает всё.

Обоснование чисел триггеров сроков:

—  14 дней — вдвое длиннее типичного спринта: PR, живущий две недели, уже не поток разработки, а отложенное решение. 7 дней — слишком рано (у крупных PR нормальный review занимает около недели), 30 — слишком поздно (PR висит месяц, прежде чем отчёт его заметит);

—  3 рабочих дня — достаточный срок, чтобы автор увидел замечание и начал править; дольше — замечание превратилось в блокер. Рабочие, а не календарные дни — иначе триггер срабатывает на все выходные;

—  оба триггера применяются к PR/MR со связанной задачей в активных статусах; PR/MR без связи — по отдельному триггеру выше, не «безопасны по умолчанию».

Параметры (14 дней, 3 рабочих дня) пересматриваются по итогам пилота через MR.

Структура пункта:

- Проблема — что произошло;

- Доказательства — Jira-ключи, PR/MR, статусы, даты;

- Значение — почему это важно;

- Предложение — что сделать (по возможности с числом), кому, когда проверить.

Если сработавших триггеров нет — вывести «значимых рисков не выявлено»

с основанием (что проверено); не выдумывать пункты для заполнения раздела.

Завершить прогнозом на следующую неделю (открытые задачи, PR/MR, блокировки), пометить как оценку, не факт.

Предложения не выдавать за согласованные поручения; дефекты не утверждать без доказательств.

## 3.2 Итоги периода

3–5 пунктов: что сделала команда; значимые завершённые и незавершённые изменения; практическое значение для бизнеса; вопросы, требующие внимания.

Цифры результата уместны; не пересчитывать показатели раздела динамики.

Переход в Done — не подтверждение выпуска в production.

## 3.3 Динамика и статистика

Раздел объединяет динамику к базе сравнения и общую статистику недели.

Отдельный блок статистики после него не выводится — каждый показатель публикуется в чате один раз.

Перед сравнением проверить сопоставимость областей: одинаковые проекты и репозитории, одинаковая методика подсчёта и доступность источников в обоих периодах. При различиях пометить динамику как ограниченно сопоставимую и не интерпретировать её как изменение работы команды.

Сравнение по каждому показателю. Формат: значение (было N), отклонение абсолютное и процентное. Процент считается как (новое − старое) / старое × 100.

При старом значении 0 процент не рассчитывается — показывается только абсолютное отклонение с пометкой «база 0».

Jira: завершённые задачи; закрытые дефекты; reopened-задачи; просроченные задачи; задачи без срока; завершённые без подтверждённого выхода в production.

Git: созданные PR/MR; слитые PR/MR; закрытые без слияния PR/MR;

открытый хвост PR/MR; медиана времени создания→слияния PR/MR;

коммиты (уникальные SHA).

Review: аккаунты с независимыми review — число Git-аккаунтов, сделавших за неделю хотя бы одно независимое review (review чужого PR/MR).

Абсолютные показатели недели (сравнение с базой не предусмотрено):

—  распределение завершённых задач по типам (фичи / дефекты / техдолг / поддержка) одной строкой; если тип задачи в проектах не заполнен —

не угадывать и строку не выводить.

При снижении: если снижение связано с крупными незавершёнными изменениями и это подтверждено данными — указать.

Метрики качества, недоступные из Jira (инциденты после релиза, MTTR), не вычислять и не оценивать — в «Качестве данных» пометить «не собирается».

Отклонения оцениваются в двух категориях:

1. Устойчивый тренд — отклонение, подтверждённое сравнением не менее чем с двумя предыдущими неделями из архива (архивный отчёт должен быть полным и подтверждённым). Трактуется как процесс.

2. Разовое существенное отклонение — оценивается по масштабу независимо от истории. Пороги:

—  качественные показатели (просроченные, reopened, возвраты из Done):

переход от 0 к ненулевому значению — уже существенное событие, «первая просрочка» — управленческий факт сам по себе.

Это правило действует независимо от размера базы;

—  количественные показатели (задачи, PR/MR, коммиты, хвост, аккаунты с независимыми review): рост не менее чем на 100% или снижение не менее чем на 50% — и при этом изменение не менее 3 единиц.

Правило малой базы относится только к количественным показателям:

при базе менее 5 единиц автоматическая существенность не присваивается независимо от процентов, отклонение фиксируется как наблюдение без управленческого пункта. Правило малой базы не отменяет отдельную оценку качественных событий.

Разовое существенное отклонение попадает в п. 3.1 с пометкой «разовое, без подтверждения трендом». Отклонения ниже порогов и без подтверждения трендом помечаются «недостаточно данных для устойчивого тренда»

и не становятся предметом управленческого внимания.

Если архива меньше двух недель — оговорить недостаточность данных для оценки тренда.

Пороги стартовые и рассчитаны на запуск: после накопления 4–6 недель архива пересматриваются через MR по фактической статистике недель;

тогда же пересматривается состав показателей раздела.

Четыре состояния метрики различаются явно:

—  «не собирается» — данных нет в источнике вообще;

—  «временно недоступно» — источник есть, но не отвечает или ответил с ошибкой в момент сбора;

—  «не удалось определить» — источник ответил, но данных не хватает (неполный охват, отсутствие нужных прав);

—  «0» — метрика собрана и равна нулю.

Не изобретать значения и не смешивать эти состояния.

Не делать выводов о дефектах по отсутствию записанного review, о продуктивности — по числу задач, PR/MR или коммитов.

## 3.4 Результаты по направлениям и участие сотрудников

Правило охвата: короткая и полная версии строятся из одного проверенного набора данных; различается детализация, но не факты и показатели.

Направления определяются автоматически по фактическим задачам и PR/MR:

—  группируй по эпикам, компонентам или повторяющимся смысловым блокам задач;

—  названия — короткие, по сути работ, не по ключам проектов;

—  каждая задача — только в одном направлении; никуда не подходит — «Прочее»;

—  перед определением направлений прочитай последний сохранённый отчёт подразделения из [ПУТЬ_К_АРХИВУ]: если там есть направление с той же сутью — используй то же название без переформулировок; если архив недоступен — назови по текущим задачам;

—  если смысловых групп меньше двух — не дроби искусственно, выведи один раздел «Результаты недели».

Каждое направление формируется в двух версиях:

—  в чате — короткая: заголовок направления, содержательные итоги и строка «Участие» с персональными счётчиками (один сотрудник —

одна строка; состав счётчиков определяется применимыми наборами п. 3.5);

—  в полной версии HTML — то же плюс сводка процесса направления, иерархия задач по сотрудникам с жизненным циклом, состояниями PR/MR и независимым review, и отдельный общий перечень PR/MR без Jira-связи (вне направлений).

Доступ по ссылке на направление определяется серверной авторизацией и правами: отказ пользователю без разрешения — штатный результат, а не ошибка отчёта.

### 3.4.1 Короткая версия (чат)

**📦 Направление: [название]**

Итоги: выполненные изменения; подтверждённые результаты; значение для бизнеса; незавершённое; подтверждённые проблемы.

Значение для бизнеса обосновывается фактами периода (что изменилось для пользователей, процессов или систем) — без декларируемых эффектов;

если значение неочевидно из задач и PR/MR — указывай фактическое следствие работ, а не предполагаемую пользу.

Участие: Фамилия Имя Отчество — счётчики применимого набора п. 3.5 (Git: создано/слито/проверено чужих/открыто; Jira: завершено/в работе/просрочено/блокировки) · Фамилия Имя Отчество — ... · ...

Перечни задач и PR/MR в чате не выводятся — только в полной версии архива.

Заголовок каждого направления в чате — кликабельная Markdown-ссылка на соответствующий раздел единого HTML-отчёта. Отдельная строка «Полная версия» не выводится. Если защищённая ссылка не готова, название остаётся текстом, а сбой фиксируется в «Качестве данных».

### 3.4.2 Полная версия (HTML и Markdown-архив)

PR/MR без Jira-связи не приписываются направлениям: один общий реестр в конце полной версии, с платформой, репозиторием, номером, автором и состоянием. В направлениях показывать только подтверждённо связанные PR/MR.

Блок направления в архиве содержит: те же итоги, строку сводки процесса и вместо строки «Участие» — полную иерархию.

**📦 Направление: [название]**

Итоги: [как в короткой версии]

Процесс: N из M PR с независимым review · медиана ожидания review — X дней · K задач из L дошли до Done за неделю, остальные — на конец недели в активных статусах [сводка — 2–3 строки, только подтверждённые данные;

Иванов Иван Иванович — 2 завершённые задачи, 2 слитых PR, коммитов: 14

• ПРОЕКТ-125 — Полное оригинальное название задачи: в работе 06.11 → review 12.11; статус на конец недели: на ревью (не Done)

Незавершённые задачи направления выводятся отдельным блоком без включения в счётчики завершённых задач сотрудников.

Атрибуция (общая для обеих версий):

—  PR/MR идентифицируется уникально по сочетанию платформы, репозитория и номера (PR #123 в двух репозиториях — два разных PR);

—  PR/MR приписывается задаче по Jira-ключу. PR/MR с ключами нескольких задач указывается под каждой из них, но в счётчиках подразделения учитывается один раз (по уникальному идентификатору из предыдущего пункта);

—  завершённые задачи приписываются сотруднику по подтверждённому исполнителю на момент завершающего перехода задачи в Done; незавершённые задачи — по исполнителю на конец отчётной недели; участие других сотрудников по истории назначений может отображаться в жизненном цикле задачи, но не увеличивает счётчик завершённых задач. Авторство PR/MR определяется по Git-аккаунту, сопоставленному со справочником. Эти показатели не смешиваются;

—  коммиты приписываются сотруднику по авторству; уникальные SHA считаются один раз в общей статистике п. 3.3; число коммитов в строке PR/MR — это коммиты данного PR/MR;

—  PR/MR без сопоставленного Git-аккаунта учитывается в общих счётчиках подразделения, но не приписывается сотруднику; расхождение —

в «Качестве данных».

Показатели сотрудника относятся только к текущему направлению:

количество завершённых Jira-задач, назначенных сотруднику; количество слитых PR/MR, автором которых он является и которые подтверждённо связаны с задачами данного направления; количество коммитов этих PR/MR, автором которых он является.

PR/MR других авторов могут отображаться под Jira-задачами сотрудника, но не включаются в его персональные Git-показатели.

Общие Git-показатели сотрудника (по всем направлениям) не дублировать в каждом направлении. Один PR/MR, связанный с задачами нескольких направлений, отображается под соответствующими задачами, но в итогах подразделения учитывается один раз. Git-активность без подтверждённой связи с направлением не распределяется между направлениями предположительно.

Следствие (не ошибка): сумма показателей по сотрудникам может быть меньше общих счётчиков подразделения — из-за Git-активности без связи с направлением, несопоставленных аккаунтов и PR/MR других авторов под задачами; это отражено в «Качестве данных».

Общие правила:

—  сотрудники без завершённых задач в данном направлении в нём не перечисляются — ни в строке «Участие», ни в полной версии:

их участие видно через общую статистику п. 3.3, аналитику по сотрудникам (п. 3.5) и «Качество данных»;

—  полный Jira-ключ и оригинальное название без сокращений; полные ФИО в архиве; в чат-строке «Участие» допускается краткая форма «Фамилия И.О.»;

—  сотрудники внутри направления — в порядке убывания количества задач;

не оформлять как рейтинг или топ; не делать выводов о личной продуктивности по числу задач, PR/MR или коммитов;

—  без заглушек «н/д», «PR не найден»; без URL и Markdown-ссылок, кроме ссылок на персональные аудиты (п. 3.5) и кликабельных заголовков направлений (п. 3.4.1);

—  список не сокращать ради объёма; итог по уникальным ключам без двойного счёта;

—  если задачи сотрудника относятся к нескольким направлениям —

распределяй по соответствующим направлениям; число задач в заголовке соответствует числу перечисленных под ним задач в данном направлении;

—  персональные агрегаты по всем направлениям (новые, слитые, проверенные PR) в архивной версии не дублируются — они выводятся один раз в п. 3.5 и в персональном аудите; в архиве — только вклад в конкретное направление;

—  имена проверяющих по-прежнему не выводятся ни в чате, ни в архиве;

в архиве фиксируется только факт независимого review («да/нет») —

этого достаточно для проверки направления и триггера «слит без независимого review».

## 3.5 Аналитика по сотрудникам

В чат выводится персональный вывод и показатели; ФИО — единственная ссылка на соответствующий HTML. Ссылки не являются доказательством сами по себе: факты должны подтверждаться исходными событиями Jira/Git.

Недельный срез участия каждого сотрудника в потоке работы: краткий вывод и ключевые показатели, со ссылкой на персональный HTML-аудит за тот же отчётный период. Данные этого раздела не являются оценкой продуктивности сотрудника — оговорка выводится один раз после заголовка раздела.

Персональные HTML-аудиты формируются отдельным процессом до запуска отчёта. Агент ищет их только в каталоге [ПУТЬ_К_ПЕРСОНАЛЬНЫМ_ОТЧЁТАМ]/YYYY-Www/<employee-id>.html и не генерирует самостоятельно. <employee-id> — стабильный безопасный идентификатор из справочника, не отображаемое ФИО.

Перед публикацией раздела агент проверяет реестр персональных аудитов (см. п. 14 шаблона employee-audit). Ссылки на персональные аудиты формируются исключительно по записям реестра со статусом «сформирован», включая исправленные версии <employee-id>-vN.html. При отсутствии реестра либо записи сотрудника ссылка не создаётся. Базовый файл <employee-id>.html используется только тогда, когда он указан в реестре как актуальная версия. Если реестр пуст или отсутствует — раздел публикуется без ссылок на аудиты с пометкой «персональные аудиты не предоставлены (смежный процесс не завершён)»; это не блокирует статус «завершён» (п. 3.6). Аудит-процесс дополнительно публикует сводный индекс аудитов (audit-index.html, п. 14 шаблона employee-audit); индекс не заменяет персональные ссылки и не является источником показателей.

Состав блока на каждого сотрудника:

[ФИО] — кликабельная ссылка на персональный HTML-аудит:

Единая схема: [ПУТЬ_К_ПЕРСОНАЛЬНЫМ_ОТЧЁТАМ]/YYYY-Www/<employee-id>.html; пример: employees/2026-W46/i.kochubey.html. Период обязателен в пути; перезапись файла другой недели запрещена.

Путь [ПУТЬ_К_ПЕРСОНАЛЬНЫМ_ОТЧЁТАМ] задаётся единой конфигурационной переменной, общей для отчётного и аудит-процессов; изменение пути — только через MR владельца шаблона.

Краткий вывод: 1–3 предложения о состоянии потока работы сотрудника по применимым источникам — что создаёт и проверяет (или ведёт задачи), что не дошло до интеграции или завершения, где накапливается работа и отсутствует обратная связь. Вывод строится по подтверждённым фактам недели; персональный HTML-аудит используется как дополнительный контекст, но не подменяет первичные Jira/Git-данные.

Показатели одной строкой, за отчётную неделю по всем направлениям вместе. Состав набора определяется применимостью источников для сотрудника; применимость устанавливается по подтверждённому характеру деятельности, а не по наличию событий:

—  набор Git (применим Git): новых PR/MR — создано сотрудником за неделю; слитых PR/MR — слито за неделю; чужих PR/MR проверено — уникальные чужие PR/MR, по которым сотрудник оставил независимое review (не события review); открытых авторских PR/MR — состояние на конец недели по всем репозиториям области, независимо от даты создания;

—  набор Jira (Git неприменим, деятельность подтверждается Jira): завершено задач — по правилам атрибуции п. 3.4; в работе — состояние на конец недели; просрочено — состояние на конец недели; подтверждённые блокировки — по истории;

—  если применимы оба источника — выводятся оба набора. Если применимость не установлена — показатели получают статус «не удалось определить», а не «не применяется». Различие подтверждённого нуля, неприменимости и недоступности сохраняется (п. 3.3, 3.6).

Правила:

—  выводятся все сотрудники, сопоставленные со справочником и имеющие за отчётную неделю либо подтверждённые события, либо значимую незавершённую работу на конец недели (открытые задачи, открытые авторские PR/MR, подтверждённые блокировки); отсутствие событий не исключает сотрудника автоматически. Сотрудник без событий и без незавершённой работы в разделе не выводится — его состояние видно в статистике п. 3.3. Нулевые значения выводятся как «0» (собранное значение, не пропуск). Несопоставленные Git-аккаунты персональных блоков не получают — они видны в общих счётчиках и «Качестве данных»;

—  показатели раздела — недельные по всем направлениям; разбивку по направлениям не дублировать (она в п. 3.4). Сверка: суммы показателей каждого набора по сотрудникам сверяются с общими счётчиками п. 3.3/3.4 с учётом несопоставленных аккаунтов (слитые PR/MR — с учётом сопоставленных аккаунтов, завершённые задачи — с учётом атрибуции п. 3.4); расхождение — в «Качество данных» с указанием причины по п. 3.6;

—  ссылка ведёт в защищённое хранилище: открытие файла регулируется правами на хранилище, а не на чат. Участник без прав при переходе видит отказ доступа — это штатная ситуация, не ошибка отчёта.

Агент ставит ссылку, не проверяя права получателя. Если чат не поддерживает кликабельные ссылки — вместо них идентификатор аудита (логин + период), по которому файл находится в хранилище;

—  ссылка ставится только на HTML, период которого совпадает с отчётным;

если HTML не найден или недоступен — блок выводится без ссылки (вывод и цифры агент считает из своих источников), расхождение —

в «Качество данных»; URL самого файла в тексте не публиковать;

—  порядок сотрудников — по алфавиту. Не оформлять как рейтинг или топ;

не сравнивать сотрудников между собой и не делать выводов о личной продуктивности по числу задач, PR/MR, коммитов или review;

—  вывод — о процессе и потоке, не о человеке; без диагнозов и оценок личности; без выдумывания причин — если причина не подтверждена данными, указывать наблюдение, а не объяснение;

—  возраст открытых PR/MR и их перечень в чате не выводить — это содержание персонального HTML; если индивидуальная ситуация попадает под триггер п. 3.1 — она оформляется пунктом там, а не здесь;

— если Jira/Git-данные доступны, но персональный HTML-аудит отсутствует, вывод и показатели сохраняются без ссылки; отсутствие аудита фиксируется в п. 3.6. Если недоступны сами Jira/Git-данные — соответствующие показатели отмечаются «временно недоступно» или «не удалось определить», без выдуманных выводов.

Отсутствие файла персонального аудита само по себе не делает раздел 3.5 недоступным.

## 3.6 Качество данных

Кратко: расхождение счётчика с данными напрямую из Jira/Git (обе цифры сохраняются); неполный охват; несопоставленные исполнители и Git-аккаунты;

состояния метрик («не собирается» / «временно недоступно» / «не удалось определить» / «0» — по п. 3.3); неподтверждённые связи; ограничения сопоставимости областей между периодами; недостаточность архива для оценки тренда; отсутствие персональных HTML-аудитов за отчётный период;

недоступность истории переходов Jira для жизненного цикла задач (п. 3.4.2);

отсутствие сводки процесса по причине нехватки данных; неполные и несохранённые архивы прошлых недель не используются как основа трендов (о несохранённом архиве агент узнаёт из служебного уведомления прошлой недели или факта отсутствия файла). Без технического журнала.

При сверке персональных значений с общими счётчиками (п. 3.3, 3.4, 3.5) агент указывает причину каждого расхождения: несопоставленные аккаунты; PR/MR без Jira-связи; PR/MR других авторов под задачами; неаддитивность метрик ревью (один PR/MR может получить ревью нескольких сотрудников).

Расхождения с персональными аудитами фиксируются по записям реестра аудитов в машиночитаемом виде; дублирование текста «Качества данных» аудита вручную не требуется.

Self-review, распределение review по сотрудникам, перечень проверяющих, review до/после merge, возраст хвоста как распределение, задачи в работе и merge-коммиты в отчёт не включены — по решению владельца шаблона;

сработавшие случаи (PR/MR без независимого review) видны в п. 3.1, а факт независимого review по каждому PR — в архивной версии п. 3.4.2.

# 4. Оформление и публикация

Режим публикации: HTML. Правила разделов 1–3.6 применяются и к краткой чат-версии, и к полной версии; различаются объём представления и способ доступа.

Общая инфраструктура: собственный сервер компании, защищённый HTTPS-домен [ДОМЕН_ОТЧЁТОВ], авторизация пользователей и разграничение прав. Руководители открывают материалы из любой сети без обязательного VPN. Публичный анонимный доступ запрещён. Наличие ссылки не заменяет проверку прав на сервере.

Обязательные параметры конфигурации: [ПУТЬ_К_ФАЙЛУ], [ПУТЬ_К_АРХИВУ], [ПУТЬ_К_ПЕРСОНАЛЬНЫМ_ОТЧЁТАМ], [КАТАЛОГ_ПУБЛИКАЦИИ], [ДОМЕН_ОТЧЁТОВ], [МЕХАНИЗМ_АВТОРИЗАЦИИ], [ПРАВИЛА_ДОСТУПА]. Значения задаёт инфраструктура; агент не придумывает домены и URL.

Единый идентификатор периода: ISO YYYY-Www по Europe/Moscow. Файлы публикуются атомарно: сначала во временный каталог, затем переключение на готовую версию; проверка существования и ответа HTTPS выполняется под сервисной учётной записью с нужными правами. Не проверять доступ личного аккаунта каждого получателя.

Если файлы персональных аудитов ещё не произведены отдельным процессом, ФИО выводится без ссылки, показатели Jira/Git сохраняются, в «Качестве данных» фиксируется отсутствие аудита. Нельзя ссылаться на файл другой недели или выдавать файл другого сотрудника.

Обязательный HTML-материал просмотра — один адаптивный index.html на подразделение и неделю: [КАТАЛОГ_ПУБЛИКАЦИИ]/ТЕМА/YYYY-Www/index.html. Он содержит все разделы отчёта и полные направления. Каждому направлению назначается уникальный стабильный якорь dir-<stable-id>. Заголовок направления в чат ведёт на index.html#dir-<stable-id>.

Необязательные материалы — персональные HTML-аудиты: [ПУТЬ_К_ПЕРСОНАЛЬНЫМ_ОТЧЁТАМ]/YYYY-Www/<employee-id>.html (например, employees/2026-W46/i.kochubey.html). Их выпускает отдельный процесс; отсутствие аудита не препятствует статусу «завершён», ФИО выводится без ссылки. HTML очищается от небезопасной разметки.

Публикация HTML не означает создание портала: допускается статический Nginx с существующим корпоративным шлюзом аутентификации и MFA. Авторизация и права проверяются на сервере, а не в клиентском JavaScript. Для разделов и сотрудников разрешения могут отличаться.

Статусы после доставки всех частей чат: «завершён» — Markdown сохранён и обязательный index.html опубликован и проверен; «доставлен, архивирование не завершено» — Markdown не сохранён (в том числе при одновременном сбое HTML; дополнительно указать «представление недоступно»); «доставлен, представление недоступно» — Markdown сохранён, но index.html не опубликован. Частичная доставка чат — «доставка не завершена». Отсутствие необязательных аудитов не меняет статус.

Повторная публикация регулируется единым правилом ниже; нельзя молча заменять ранее опубликованную редакцию или ссылку.

- Заголовки разделов отчёта — отдельной строкой, жирным, с фиксированным маркером раздела. Маркеры закреплены жёстко, менять между неделями нельзя:

🚦 — статус; ⚠️ — на что обратить внимание; 📋 — итоги; 📈 — динамика и статистика; 📦 — направления; 🧑‍💻 — аналитика по сотрудникам;

🧾 — качество данных.

Если чат не поддерживает жирное начертание — заголовок ЗАГЛАВНЫМИ БУКВАМИ с тем же маркером. Не выдумывать другие маркеры и не пропускать.

Если 🧑‍💻 не отображается корректно в целевом чате — запасной маркер 👤.

- Каждый пункт, задача и PR/MR — на отдельной строке; между смысловыми блоками — пустая строка.

- Слова и идентификаторы (Jira-ключи, номера PR/MR) не разрывать при переносе: каждая задача, PR/MR и пункт — целиком на своей строке.

- В чат разрешены только Markdown-ссылки в названиях направлений на защищённые HTML-материалы (п. 3.4.1) и в ФИО на персональные HTML-аудиты (п. 3.5). Не выводить сырые URL, Jira/Git-ссылки и ссылки на интерфейс репозитория.

Для Jira-задач и PR/MR показывать идентификаторы без URL.

- Если отчёт превышает 3000 символов — разделить на последовательные сообщения длиной не более 3000 символов каждое, с учётом заголовка «Часть X из N» и финальной строки. Не разрывать отдельную Jira-задачу или PR/MR между сообщениями. Правило относится к чат-версии; архивная версия ограничением 3000 символов не связана.

- Последнюю часть чат-версии завершать строкой «Отчёт завершён · [название подразделения] · YYYY-Www». Не отправлять эту строку, если полный отчёт не сформирован. Строка — удобочитаемый признак для читателя;

фактическая доставка и запись архива подтверждаются технической проверкой, не только текстом.

- Порядок публикации: (1) собрать полную версию по п. 3.4.2, включая общий реестр несвязанных PR/MR; (2) сохранить Markdown в репозитории по пути [ПУТЬ_К_АРХИВУ]/ТЕМА/YYYY-Www.md (ISO-неделя отчётного периода); (3) сформировать и опубликовать обязательный index.html, проверить HTTPS и якоря; (4) проверить доступные персональные HTML-аудиты; (5) отправить краткую версию в чат. Ссылки добавлять только на существующие проверенные материалы; при сбоях — текст без недоступных ссылок, видимая пометка «Подробные материалы временно недоступны» и служебное уведомление.

Markdown — канонический технический архив для трендов и повторной генерации представлений.

Адреса HTML строятся только после успешной публикации файлов; адрес репозитория не подставляется вместо защищённой ссылки на представление.

При сбое Markdown-архива — статус «доставлен, архивирование не завершено» после доставки чат; при одновременном сбое HTML дополнительно указать «представление недоступно». При сбое только index.html — «доставлен, представление недоступно». Отсутствующие персональные аудиты не блокируют завершение: ФИО без ссылки, причина в п. 3.6.

- При сбое на любом шаге — явное сообщение об ошибке и повторная попытка только неудавшейся операции (конкретной части, записи архива), не пересборка всего отчёта. Отчёт, отправленный частично, не считается опубликованным. Если все части отправлены, но запись в архив не удалась —

статус «доставлен, архивирование не завершено»; полностью завершённым запуск не считается до успешной записи архива и публикации обязательных материалов.

- Повторная публикация: в чат и HTML указывать «Повторная публикация (исправление): [что изменено]»; сохранить новый Markdown YYYY-Www-rev2.md и соответствующий HTML в отдельном каталоге редакции; предыдущие версии не затирать. Ссылки новой публикации ведут на новую редакцию; для трендов использовать только последнюю подтверждённую полную редакцию.

- Сохранение Markdown в архив обязательно для воспроизводимости и трендов. HTML-представление — формат просмотра, не отдельный источник метрик. При несовпадении версий ссылки должны вести на ту же редакцию, что опубликована в чат.

# 6. Чек-лист качества перед публикацией

- [ ] Авторизация и разграничение доступа настроены на сервере; внешнее открытие с личного устройства возможно только после входа; доступ без авторизации закрыт.

- [ ] HTML: проверены index.html и якоря всех направлений, защищённые HTTPS-ссылки; персональные аудиты — только существующие за нужную неделю; ссылки не ведут в интерфейс GitHub/GitLab — ограничение действует для материалов отчёта; для персональных аудитов действует п. 10.4 шаблона employee-audit.

- [ ] Шаблон прочитан из репозитория; при недоступности — остановка с ошибкой, работа по памяти запрещена

- [ ] Источники проверены на доступность и полноту периода до анализа

- [ ] Сопоставимость областей проверена (п. 3.3); при различиях —

пометка «ограниченно сопоставима»

- [ ] Статус недели определён по лестнице п. 3.0; критичность — только по данным; уровень «не определён» — только после проверки пунктов 1–2

- [ ] Оба периода собраны по правилу недели (полузакрытый интервал [пн 00:00, пн 00:00), Europe/Moscow); показатели состояний прошлой недели восстановлены по истории, не по текущему состоянию источников

- [ ] Динамика посчитана по каждому показателю п. 3.3; формула процента соблюдена; при базе 0 — абсолютное отклонение с пометкой

- [ ] Аномалии оценены по порогам п. 3.3: качественные — 0→ненуль независимо от базы; количественные — рост ≥100% или снижение ≥50% при изменении ≥3 единиц; база <5 — только наблюдение; разовые существенные — с пометкой; ниже порогов — «недостаточно данных»

- [ ] Каждый показатель опубликован в чате один раз; отдельного блока статистики после п. 3.3 нет

- [ ] Задачи уникальны (история Done), нет двойного счёта

- [ ] Атрибуция по п. 3.4: PR/MR уникальны по платформе+репозиторию+номеру; задачи — по исполнителю на момент завершающего перехода в Done (незавершённые — по исполнителю на конец недели), персональные Git-показатели — только авторские (PR других авторов под задачами не включаются в персональные цифры); заголовки и строка «Участие» — только показатели своего направления

- [ ] П. 3.5: наборы показателей каждого сотрудника соответствуют применимости источников (Git/Jira/оба); суммы каждого набора сверены с п. 3.3/3.4 с учётом несопоставленных аккаунтов; в раздел включены сотрудники с событиями или значимой незавершённой работой; ссылки — только на HTML отчётного периода; выводы о потоке, не о продуктивности; порядок алфавитный

- [ ] Ссылки на персональные аудиты сформированы исключительно по записям реестра со статусом «сформирован» (включая исправленные версии); при отсутствии реестра либо записи сотрудника ссылка не создана; при отсутствии реестра раздел опубликован с пометкой «персональные аудиты не предоставлены», без блокировки статуса

- [ ] В выборку включены все задачи проектов, без фильтрации по исполнителям; несопоставленные отражены и отмечены

- [ ] Связи PR/MR подтверждены Jira-ключом

- [ ] Триггеры сроков PR/MR применены только к связанным задачам в активных статусах; PR/MR без связи проанализированы отдельно без выдуманных ключей

- [ ] Названия направлений сверены с последним сохранённым отчётом;

изменения названия обоснованы сменой сути работ

- [ ] Полные перечни задач и PR/MR — только в архивной версии (п. 3.4.2);

в чат-версии направлений — итоги и строка «Участие», перечней нет

- [ ] Архивная версия содержит: сводку процесса по каждому направлению, жизненный цикл задач (или текущий статус с пометкой, если история переходов недоступна), состояния всех PR/MR направления, факт независимого review («да/нет») по каждому PR/MR и отдельный общий перечень PR/MR без Jira-связи;

описания задач — из Jira, без выдумывания

- [ ] Имена проверяющих не выводятся ни в чате, ни в архиве;

персональные агрегаты по всем направлениям — только в п. 3.5

- [ ] Значение для бизнеса в направлениях — фактическое следствие, не декларация

- [ ] Done ≠ production соблюдён; триггер «Done без production» применён только к значимым задачам

- [ ] «На что обратить внимание» стоит сразу после статуса; проверены все триггеры п. 3.1; при более четырёх — выбор по значимости, остальные видны в статистике; при пустом результате — «значимых рисков не выявлено»

с основанием

- [ ] Метрики различены по четырём состояниям п. 3.3; значения не придуманы

- [ ] Заголовки разделов оформлены по п. 4: маркеры соответствуют, жирное начертание или ЗАГЛАВНЫЕ
