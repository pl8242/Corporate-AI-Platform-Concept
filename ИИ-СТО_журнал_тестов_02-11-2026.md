## Хронология запросов, ответов и оценок

### T01. «Что сделала команда WEB за последнюю завершённую неделю? Покажи завершённые задачи Jira и связанные PR/MR в Git. Укажи ссылки на источники»
**Ответ:** 86 завершённых Jira; 25 задач связаны с 27 merged GitLab MR; 61 задача без явной связи с MR. Отсутствие MR не доказывает отсутствие работы, merge не равен production.
**Оценка:** исходный показатель 86 не воспроизведён; точные параметры первоначального JQL и логи недоступны. **Открыто**.

### T02. «Сравни 19–25 октября и 12–18 октября по WEB» (смысл вопроса; точная формулировка не сохранена)
**Ответ:** 72 → 92 решённые Jira; 28 → 39 merged MR основного репозитория; 27 MR — подмножество со связью с Jira, 39 — все merged MR. Агент отметил расхождение с прежними 86.
**Оценка:** показатели Jira 92 подтверждены контрольным срезом; Git MR отдельно не сверялись. **Частично**.

### T03. «Почему 86 против 92, а 27 против 39?» (смысл вопроса)
**Первый ответ агента:** 86 resolved + 6 DECLINED = 92 — **некорректная интерпретация**.
**Исправленный ответ:** 98 всего = 92 «Решенные» + 6 DECLINED; шесть решённых задач, отсутствовавших в первоначальных 86: PWEB-35552, PWEB-35130, PWEB-35293, PWEB-35342, PWEB-35472, PWEB-35471. Причина пропуска не установлена. 27 Jira-linked MR и 39 всех merged MR — разные метрики.
**Оценка:** числовая коррекция подтверждена, причина исходного 86 — **открыта**.

### T04. Проверка отдельных задач PWEB-35552 и PWEB-35130
**Действие пользователя:** сверка полей в Jira. PWEB-35552: дата решения 23.10.2026, статус «Решенные», решение «Готово»; PWEB-35130: дата решения входит в период.
**Оценка:** два примера подтверждают необходимость расследования первоначального пропуска; для PWEB-35130 остальные поля не сверялись в этой переписке.

### T05. «Выполни новый запрос к Jira по проекту PWEB за 19–25 октября… без ограничения по статусам; покажи количество, распределение, JQL и пагинацию»
**Ответ:** 22, все «Решенные», 0 DECLINED. JQL дополнен `assignee in (...)` по 28 сотрудникам WEB, хотя ограничение не запрашивалось. `returned=22`, `total=22` (по словам агента).
**Оценка:** **ошибка области запроса**: проектная аналитика заменена аналитикой назначений сотрудников.

### T06. «Повтори строго: project=PWEB AND resolutiondate…; не добавляй фильтры»
**Ответ:** 98 = 92 «Решенные» + 6 DECLINED. Параметры: `project_key=PWEB`, `jql_filter=resolutiondate >= "2026-10-19" AND resolutiondate < "2026-10-26"`, `limit=100`, `offset=0`; `returned=98`, `total=98`, `has_more=false`.
**Оценка:** **совпало с Jira**.

### T07. «Почему добавил assignee? Это инструкция агента или dev_analytics? Как различаешь проект и отдел?»
**Ответ:** правило из конфигурации агента для отдела WEB; агент ошибочно применил его к проекту PWEB. Инструмент сам фильтр не добавлял. Для проекта — project; для отдела — список Jira ID сотрудников; для отдела в проекте — оба фильтра.
**Оценка:** полезное объяснение агента, **не независимо подтверждено просмотром конфигурации**.

### T08. «Сколько задач было решено в проекте PWEB за 19–25 октября 2026 года?»
**Ответ:** 98 задач с `resolutiondate`, из них 92 «Решенные» и 6 DECLINED; без assignee.
**Оценка:** численно верно, но формулировка «решено» требует отделять 92 успешные от 98 с датой решения.

### T09. «Сколько задач выполнили сотрудники отдела WEB за 19–25 октября 2026 года?»
**Ответ:** 22 задачи **в PWEB**, хотя проект в вопросе не указан.
**Оценка:** **ошибка переноса контекста** из предыдущего запроса; дополнительно фильтр ID занижал результат.

### T10. «Сколько задач сотрудники отдела WEB решили в проекте PWEB за 19–25 октября 2026 года?»

**Оценка:** запрос по смыслу сформирован верно, но **число занижено** из-за идентификаторов в JQL.

### T11. «Почему ограничил WEB проектом PWEB? Проверь все проекты без project=PWEB»
**Ответ:** агент признал перенос контекста; запросил 9 доступных проектов APP, CRMSPRINT, MA, OPS, PAYM, PO, PWEB, ROUTINE, SYS. По его словам, только PWEB дал 22, остальные 0; каждый проект запрашивался отдельно, так как `project_key` обязателен. `allowlisted_only=true` — область доступа ограничена девятью проектами.
**Оценка:** область проверки расширена, но **результат 22 всё ещё занижен** по причине Jira ID; нули по другим проектам требуют перепроверки с рабочими логинами.

**Независимая проверка:** пользователь подтвердил соответствие сотрудников справочнику WEB.
**Оценка:** **состав подтверждён**, но исторический состав 19–25.10 и пригодность ID для JQL не были подтверждены.

### T13. «Почему Jira по списку сотрудников показывает 72 задачи (68 решённых, 4 DECLINED), а ты 22? Проверь JIRAUSER… и логины»

**Оценка:** **подтверждённый дефект формирования JQL по идентификаторам**. Повторный запрос корректен, но постоянное исправление агента не подтверждено.

## Минусы и открытые вопросы
- Некорректное использование `JIRAUSER...` в JQL `assignee`: 22 вместо 72, пропущено 50 задач.
- Агент переносил фильтр PWEB из предыдущего вопроса и путал проектную аналитику с отделом.
- Источник исходного 86 не установлен; исправление отдельного дефекта не доказывает его причину.
- Проверка других восьми проектов выполнена с прежним некорректным фильтром — **нули нужно перепроверить** после исправления.
- 26 задач PWEB без исполнителя не должны автоматически приписываться WEB.
- Нет подтверждённого исторического состава отдела на анализируемую неделю.
- Нет подтверждения автоматических публикаций в Telegram, GitLab-метрик 27/39 и production-релизов.
